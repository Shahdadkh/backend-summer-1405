# Task: Build a "Task Manager" REST API (Backend Only)

**Prerequisite knowledge:** Express basics, Express Router, static files.

**Goal:** Build a working Express backend for a Task Manager. This is a backend-only exercise — no frontend, no UI. You'll interact with it entirely through Postman/Thunder Client/curl. I'm giving you goals and thinking questions, not step-by-step instructions. You decide the "how," and be ready to explain your choices.

No database yet — use an in-memory array first, then a JSON file for persistence. We'll cover proper error handling, validation, and logging middleware later — don't reach for those yet, even if you've seen them elsewhere. Keep this to what you've actually learned.

---

## Stage 1 — Design Before You Code

Before writing a single route, design the API on paper (or a markdown file).

- Resource: `tasks`. Each task has `id`, `title`, `completed`, `createdAt`.
- Design the REST endpoints (method + path + purpose) for full CRUD.
- Decide your folder structure (routes/, controllers/, data/, etc.) — you choose, but be ready to explain *why*.
- Write down: what status code should each endpoint return on success? On failure?

**Thinking questions:**
1. Why might you split "routes" from "controllers" instead of writing logic directly in the route file?
2. If someone requests a task that doesn't exist, what should happen? What status code, and why not just 200?

**Deliverable:** A short `DESIGN.md` with your route table and folder plan. No code yet.

---

## Stage 2 — Build the CRUD API (In-Memory)

Implement your design using `express.Router()`. Use an in-memory array as your "database."

Requirements:
- Full CRUD for `/api/tasks` (GET all, GET one, POST, PUT/PATCH, DELETE)
- Use `express.json()` correctly — figure out *where* it needs to go and why.
- The router must be mounted from a separate file, not defined directly in `app.js`/`server.js`.
- No middleware libraries for validation/errors/logging — if you need to reject bad input, do it with a plain `if` check inside the route handler and the right status code. That's enough for now.

**Thinking questions:**
1. What happens right now if you `POST` without a `title`? Should something stop it? How would you check for that with just an `if` statement?
2. Should `id` be generated by the client or the server? Why?
3. Try deleting a task that doesn't exist. What does your app currently do? Is that acceptable?

**Deliverable:** Working CRUD tested manually. Notes on your tests, including at least one failing case you tried on purpose and what your app did.

---

## Stage 3 — Serve Static Files for Task Attachments

Add the ability to attach a file to a task (e.g. an image or doc), using `express.static()` — no frontend involved, just serving the files back over HTTP.

- Create an `uploads/` (or similar) folder and serve it as static files at some path, e.g. `/files`.
- Add a field to your task, like `attachmentPath`, that stores the filename.
- For now, you can manually drop files into the folder yourself (you haven't learned file upload handling yet) — the point is understanding how `express.static()` maps a folder to a URL path.
- A `GET /api/tasks/:id` response should include a usable URL for its attachment, if it has one.

**Thinking questions:**
1. Your API lives at `/api/tasks` and your static files are served at `/files`. How does Express decide which handler responds to a given request? What would happen if these two paths overlapped?
2. If someone requests a file that doesn't exist in `uploads/`, what does `express.static()` do by default? Try it and observe.
3. Should the `uploads/` folder be publicly listable (i.e. can someone see all filenames just by browsing)? What does that mean for how you name files?

**Deliverable:** A task with a real attachment, retrievable via a working static URL through your API response.

---

## Stage 4 — Persistence + Refactor + Stretch

**Part A — Persistence:** Replace the in-memory array with reading/writing a `tasks.json` file, so data survives a server restart.
- Decide: read the file on every request, or load once into memory and write-through on changes? Pick one and be ready to defend it.

**Part B — Stretch (pick at least 2):**
- Add filtering: `GET /api/tasks?completed=true`
- Add search: `GET /api/tasks?search=keyword`
- Add pagination: `GET /api/tasks?page=1&limit=10`
- Add a `PATCH /api/tasks/:id/toggle` shortcut endpoint just for toggling `completed`
- Organize routes into resource-based routers if you haven't already (e.g. separating task routes cleanly from any future resource)

**Thinking questions:**
1. What could go wrong with reading/writing a JSON file if two requests hit the server at nearly the same time? You don't need to solve this — just explain the risk in your own words.
2. Look back at your Stage 1 design. What did you get wrong or underestimate? Write a few honest sentences.

**Deliverable:** Final working app + a short `RETRO.md` answering the questions above.
